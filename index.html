LOG_01 — SEP 2026 — 4 MIN READ

Reproduce first, fix second: my production-bug checklist

The fastest way I know to fix a production bug is to reproduce it on demand before touching any code. A reliable reproduction turns a vague ticket into a loop you can test every fix against: trigger it, change one thing, watch it disappear.

  1. Read the ticket and the logs. Note the app version, environment, user role, and exact steps before anything else.
  2. Search the stack trace first. The first Caused by line usually names the real culprit: 
    grep -i "exception\|caused by" app.log | tail -20
  3. Reproduce on test. Same data, same steps. If it won't reproduce, the bug is in data or config — not code.
  4. Isolate one variable. Config vs. code vs. data. Change one thing at a time.
  5. Apply the smallest fix, verify, document. Re-run the reproduction, then write down steps so the next ticket goes faster.

TAGS: SUPPORT / DEBUGGING / LOGS

LOG_02 — SEP 2026 — 5 MIN READ

Hospital Management System: what Spring Boot + Angular taught me

I built a full-stack Hospital Management System with Java, Spring Boot, MySQL and Angular to learn how real apps fit together: patients, doctors, appointments and billing with actual CRUD and an auth flow. The biggest lesson was layering — thin controllers, a service layer for rules, repositories for data.

A minimal controller sets the pattern for every entity in the app:

@RestController
@RequestMapping("/api/patients")
public class PatientController {
  private final PatientService patients;

  public PatientController(PatientService patients) {
    this.patients = patients;
  }

  @GetMapping("/{id}")
  public Patient getOne(@PathVariable Long id) {
    return patients.findById(id);
  }
}

Two gotchas worth knowing: enable CORS for the Angular dev server or every request fails silently in the browser, and keep DTOs separate from entities so internal fields never leak into API responses.

LOG_03 — SEP 2026 — 3 MIN READ

SQL queries I actually use in support

Most support tickets end at the database: is the row there, when did it change, and how many others look like it? Three query shapes answer the majority of my tickets — counts by status, recent rows for one user, and duplicates.

SELECT status, COUNT(*) AS tickets
FROM support_tickets
WHERE created_at >= CURDATE() - INTERVAL 7 DAY
GROUP BY status
ORDER BY tickets DESC;

Count-by-status first tells me whether one user is confused or a whole release is broken. Then I pull the newest rows for the affected account, compare timestamps against the deploy log, and only then escalate to the dev team — with row IDs attached.
